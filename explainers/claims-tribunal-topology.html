Claims Tribunal: every component, where it runs, and what calls what

One FastAPI process is the spine. Locally it is uvicorn tribunal.api:app on :8423 behind a Vite dev server on :5802; in Azure the same code plus an MCP endpoint runs as tribunal.mcp_http:app in a Container App behind API Management. Every adjudication is an Agent Framework graph (OCR → Structure → fan-out Adjuster ‖ Fraud ‖ Policy → fan-in Arbiter) whose executors call three Azure data planes: the Foundry account (Mistral OCR endpoint, Responses API for six prompt agents, embeddings), Azure AI Search (four indexes), and Application Insights (spans + one tribunal.verdict record that feeds an alert rule). State lives in AI Search indexes, Blob and two JSON files; nothing else is stateful.

One adjudication, call by call crash4 in the browser, 44-49 s wall clock

1
tribunal/ui/src/App.tsx run()

The bench posts multipart sample=crash4 (or uploaded statement pages + a photo) to POST /adjudicate and reads the response body as a stream, parsing SSE frames by hand because EventSource cannot POST. Events: claim.start, agent.start, agent.token, agent.done, claim, evidence, verdict, error, end.

show call
POST http://localhost:8423/adjudicate\nContent-Type: multipart/form-data; sample=crash4\n→ 200 text/event-stream\nevent: claim.start\ndata: {{\"claim_id\": \"CLM-20260907-AF6B2E\", \"sample\": \"crash4\"}}
2
tribunal/api.py → tribunal/af_workflow.py adjudicate()

The route builds an asyncio.Queue, starts workflow.run(ClaimIntake, stream=True) and yields each TribunalEvent the executors emit via ctx.yield_output; the runner polls its event queue while a superstep is still running, so tokens stream mid-step rather than at step boundaries.

3
OcrExecutor → challenge-2/agents/ocr_agent.py extract_text_with_ocr

Both statement pages go to the Foundry account's Mistral OCR route in parallel threads, base64 image in the body, api-key header; the response's pages[].markdown is joined into one text.

show call
POST https://msagthack-aifoundry-6ahymubsyajs6.cognitiveservices.azure.com/providers/mistral/azure/ocr\napi-key: <AI_FOUNDRY_KEY>\n{{\"model\": \"mistral-document-ai-2512\", \"document\": {{\"type\": \"image_url\", \"image_url\": \"data:image/jpeg;base64,…\"}}}}\n→ {{\"pages\": [{{\"markdown\": \"# ACCIDENT STATEMENT FORM …\"}}]}}
4
StructureExecutor → tribunal/foundry.py run_agent()

First call per process creates the agent version (agents.create_version(PromptAgentDefinition(model='gpt-4.1-mini', instructions=…)), visible in the Foundry portal); every call after that is a streaming Responses request with agent_reference. Auth is an Entra bearer token from DefaultAzureCredential (the az CLI login of the lab user).

show call
POST https://msagthack-aifoundry-6ahymubsyajs6.services.ai.azure.com/api/projects/msagthack-aiproject-6ahymubsyajs6/openai/v1/responses\nAuthorization: Bearer <entra token>\n{{\"input\": [{{\"role\": \"user\", \"content\": [{{\"type\": \"input_text\", \"text\": \"OCR TEXT: …\"}}]}}],\n \"stream\": true, \"agent_reference\": {{\"name\": \"TribunalStructureAgent\", \"type\": \"agent_reference\"}}}}\n→ event stream: response.output_text.delta {{\"delta\": \"{{\\n \\\"policy_number\\\"\"}} …
5
tribunal/workflow.py gather_evidence()

Four retrievals in one asyncio.gather: prior claims (client-side embedding of the claim summary, pure vector k=5 on prior-claims), policies (semantic hybrid on insurance-documents-index to pick the document, then every chunk of that file by $filter=file_name eq …), adjuster precedents (vector, precedents), and the damage photo (Responses call to TribunalPhotoDescriber with input_image, embed the description, vector k=4 on claim-photos). The evidence event carries all four; the UI's evidence board renders it.

show call
POST https://msagthack-aifoundry-6ahymubsyajs6.cognitiveservices.azure.com/openai/v1/embeddings   api-key\n{{\"model\": \"text-embedding-3-large\", \"input\": \"policy_number: COMM-AUTO-001 …\"}}\n\nPOST https://msagthack-search-6ahymubsyajs6.search.windows.net/indexes/prior-claims/docs/search?api-version=2024-07-01   api-key\n{{\"vectorQueries\": [{{\"kind\": \"vector\", \"vector\": [3072 floats], \"k\": 5, \"fields\": \"content_vector\"}}], \"top\": 5}}\n→ CLM-0412 @search.score 0.781 (same VIN, paid $4,850)\n\nPOST …/indexes/insurance-documents-index/docs/search   queryType=semantic, semanticConfiguration=insurance-semantic, search + vectorQueries\nPOST …/indexes/insurance-documents-index/docs/search   $filter=file_name eq 'commercial_auto_policy.md', top=100\n\nPOST …/indexes/claim-photos/docs/search   vector of the photo description → CLM-0412 crash4.jpg 0.944
6
AdjusterExecutor ‖ FraudExecutor ‖ PolicyExecutor fan-out

Three concurrent Responses streams. Adjuster gets the claim JSON plus the photo as input_image; Fraud gets the claim, the five prior claims, the photo matches, the precedents and the photo; Policy gets the claim, the whole policy document and the precedents. Each token becomes an agent.token event; each agent ends with prose then ===JSON=== and a typed object (Opinion). App Insights shows the three agent * spans starting within 2 ms of each other.

7
ArbiterExecutor (fan-in) → build_verdict → record_verdict verdict

The fan-in handler receives list[Opinion] once all three have landed and calls the Arbiter with the claim, the three opinions, the precedent block and the photo block. Its JSON carries decision, confidence, payout numbers, disagreements, referral reason, clauses[{{clause, evidence_refs[]}}] and the claimant letter. Python computes net = max(0, min(covered, limit) − deductible), attaches what_if for the slider, sets span attributes and writes the tribunal.verdict log record, then emits verdict. Fraud never denies: suspected fraud refers to the SIU.

8
tribunal/telemetry.py → Application Insights OTel

The azure-monitor-opentelemetry exporter batches spans and log records to the regional ingestion endpoint. One trace per claim: tribunal.adjudicate with six agent * children carrying gen_ai.agent.name, gen_ai.request.model, claim.id; the verdict record carries tribunal.decision, tribunal.fraud_score, tribunal.net_payout.

show call
POST https://swedencentral-0.in.applicationinsights.azure.com/v2.1/track\n[{{\"name\": \"RemoteDependency\", \"data\": {{\"baseData\": {{\"name\": \"agent fraud\", \"duration\": \"00:00:12.6\", \"properties\": {{\"claim.id\": \"CLM-…\", \"gen_ai.agent.name\": \"fraud\"}}}}}}}}, …]\n\nKQL (alert, every 5 min over 15 min):\nAppTraces | where Message has \"tribunal.verdict\" | extend fraud_score = todouble(Properties[\"tribunal.fraud_score\"]) | where fraud_score > 0.6
9
tribunal/ui/src/App.tsx → POST /decision → tribunal/precedent.py human sign-off

Approve / Deny / Override sends {{claim_id, human_decision, reason, verdict}}. The API appends the audit row to decisions.json, then record_precedent writes a document to the precedents index (embedding of the ruling text) and polls get_document until AI Search has committed it, so the very next tribunal can cite it. Response: {{ok, count, precedent_id}}.

show call
POST /decision  {{\"claim_id\": \"CLM-20260907-AF6B2E\", \"human_decision\": \"override\", \"reason\": \"SIU cleared VIN reuse: bill of sale June 2025\", \"verdict\": {{…}}}}\n→ POST …/indexes/precedents/docs/index  {{\"value\": [{{\"@search.action\": \"mergeOrUpload\", \"id\": \"PREC-CLM-20260907-AF6B2E-140327\", …}}]}}\n→ GET  …/indexes/precedents/docs/PREC-… (poll until 200)\n→ {{\"ok\": true, \"count\": 3, \"precedent_id\": \"PREC-CLM-20260907-AF6B2E-140327\"}}
10
tribunal/ui/src/Claimant.tsx → POST /appeal → tribunal/appeal.py appeal

The claimant page loads GET /claims/{{id}} (verdict, decisions, appeals from claims.json) and posts the appeal text plus an optional photo. adjudicate_appeal re-runs evidence gathering with the appeal text folded into the query, re-hears the three specialists with verdict v1 in their context, then the Appeals Arbiter answers v1 clause by clause. The API promotes v2 to the standing verdict and emits appeal.verdict {{v1, v2, outcome, diff}}; outcome is overturn only if the decision actually changed.

show call
POST /appeal  multipart claim_id=CLM-…, appeal_text=\"I bought the Outback from Andrew Bennett in June 2025 …\", photo=<optional>\n→ text/event-stream … event: appeal.verdict\ndata: {{\"outcome\": \"uphold\", \"diff\": [{{\"field\": \"confidence\", \"v1\": 0.9, \"v2\": 0.95}}], \"v2\": {{\"decision\": \"refer\", …}}}}
11
tribunal/mcp_server.py · tribunal/mcp_http.py MCP

Two transports, one tool set. Locally VS Code (.vscode/mcp.json) or Claude Desktop spawns the stdio server, which calls the REST API with httpx and returns the verdict dict (adjudicate_claim streams the SSE and collects verdict). In Azure the same tools are served over streamable HTTP at /mcp inside the container, and API Management fronts them at /tribunal-mcp.

show call
stdio:   {{\"jsonrpc\": \"2.0\", \"method\": \"tools/call\", \"params\": {{\"name\": \"adjudicate_claim\", \"arguments\": {{\"sample\": \"crash1\"}}}}}}\n         → python httpx POST http://localhost:8423/adjudicate → verdict {{\"decision\": \"deny\", …}}\n\nhttp:    POST https://msagthack-apim-6ahymubsyajs6.azure-api.net/tribunal-mcp   (JSON-RPC, Accept: text/event-stream)\n         → APIM → https://claims-tribunal.niceglacier-506f72ec.swedencentral.azurecontainerapps.io/mcp → in-process tools → REST routes on :8000
12
Azure Monitor → action group alerting

Independently of any request, Azure Monitor runs the scheduled query every 5 minutes over the last 15 minutes of AppTraces; any tribunal.verdict with fraud_score > 0.6 fires tribunal-fraud-referrals (severity 2) → action group tribunal-alerts (email). This is the only push-style path in the system; everything else is request/response or SSE.

Local versus Azure runtime

The same Python package runs in both places. Locally the demo hits tribunal.api:app under uvicorn --reload (any save of tribunal/*.py restarts it mid-request). The container runs tribunal.mcp_http:app, a Starlette app that mounts the REST routes and the MCP streamable-HTTP transport at /mcp; its image is a snapshot built by az acr build at deploy time, so code changes after the last deploy_aca.sh are local-only until redeployed. Both call the identical Azure data planes with the same .env values (as ACA secrets in the cloud).

Gotchas

  • uvicorn --reload watches tribunal/*.py: do not save Python during a live demo.
  • Foundry agent versions are created once per process; a restart creates new versions (the portal accumulates them).
  • AI Search commits asynchronously: record_precedent polls get_document before returning, otherwise the next tribunal misses the ruling.
  • Mistral OCR deployment has capacity 5: concurrent runs hit 429 and back off 30 s.
  • ACA and APIM have no auth; the public endpoints spend gpt-4.1-mini quota while up.
  • Lab policy forces disableLocalAuth on new Cognitive Services accounts: Document Intelligence works only with Entra.
  • APIM Consumption is not offered in swedencentral; BasicV2 was provisioned instead.
